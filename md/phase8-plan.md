## 2. 배경과 목표

임의 점수 대신 서버 검증 근거를 사용하고 통과한 에셋만 최종 확정·다운로드할 수 있게 한다.

- [전체 개발 플랜](development-plan.md): 제품 범위·DB/API 계약·최종 완료 기준의 기준 문서.
- [Phase 진행 규칙](phase-development-process-rules.md): 시작·테스트·보고·완료 게이트.

- [Phase 7 계획](phase7-plan.md), [체크리스트](phase7-test-checklist.md), [결과](phase7-result.md), [HTML](phase7-result.html)을 확인했다. Phase 7은 `PAUSED`: 임시 UI만 완료, 실제 공급자·게시 가이드·생성은 보류다. 사용자는 2026-09-23 Phase 8 독립 서버·다운로드 구현을 명시 승인했다. 전체 완료 게이트는 계속 미충족이며 예외 범위는 16절에 기록했다.
- 필요한 인수인계: Phase 7 실제 에셋·채택·게시 규칙/버전, Phase 5 job, Phase 4 파일/소유권.

후속 Phase를 미리 계획하는 것은 허용하되 구현은 번호 순서대로 진행한다. 이전 Phase의 실패·차단·이월 항목이 이 단계의 완료 기준에 영향을 주면 먼저 해결하거나 범위/계약 변경을 기록한다.

## 4. 현재 상태 조사

착수 시 기존 화면은 Phase 4 서버 갤러리로 전환되어 있었다. 생성·검증은 비활성, 최종 목록·라이브러리는 서버 조회이며 ZIP 기능은 없었다. 이전 mock/verify 파일이 남아 있지만 새 판정은 이를 사용하지 않는다.

현재 작업 트리에 Phase 1~7 미커밋/미추적 파일이 다수 있으며 보존한다. Next 16.3.3의 로컬 route 및 data-security 가이드를 확인했다. DB/auth/jobs/storage/admin 및 unit/integration/i18n/E2E scripts가 이미 존재한다. assets·jobs·brand_guides JSONB와 storage_tickets를 재사용하며 새 SQL migration/seed/의존성은 추가하지 않는다.

## 5. 구현 범위

검증 adapter·규칙별 pass/warn/reject/unknown·설명/근거/엔진/가이드 버전, 재검증, 서버 최종 확정/취소·동시성, 프로젝트 라이브러리/커버/집계, 실제 단일 다운로드·선택 ZIP·만료 정리를 구현한다.

이 단계에서 추가·변경하는 사용자/관리자 문구는 ko/en 파일 언어팩에 함께 반영한다. 업무 데이터 번역은 `localized_contents`만 사용하고, 고정 UI·랜딩·메일 문구는 DB로 옮기지 않는다.

## 6. 제외 범위

운영자 판정 덮어쓰기·가이드 없는 최종 확정·자동 권리 판정. 최종 취소를 원본 파일 삭제로 처리하지 않는다.

결제·구독, 조직 협업, 범용 CMS, 자동 침해 신고는 전체 초기 범위에서 제외한다. 새로운 비용·제품 정책·공개 계약이 필요하면 구현 전에 전체 플랜과 이 문서의 변경 이력을 갱신한다.

## 7. 결정·가정·질문

공급자·실제 품질 기준은 사용자 요청으로 보류한다. 독립 구현은 모든 규칙 pass만 최종화, unknown/부분 실패는 차단, 새 최종화는 현재 active 게시 가이드만 허용, 과거 최종 근거 보존을 적용한다. ZIP 50개/100MiB/24시간 등 구현 기본값과 근거는 16절에 기록했다.

권장안과 확정 사항을 구분한다. 이 문서 작성에는 추가 승인이 필요하지 않으며, 미결정 항목은 해당 구현의 시작 게이트에서 해결한다. 실제 과금·메일 발송·외부 데이터 변경 검증은 진행 규칙 8.6에 따라 승인된 대상과 환경에서만 수행한다.

## 10. 테스트 계획

실행 scripts는 `corepack pnpm typecheck`, `lint`, `build`, `test:unit`, `test:integration`, `test:e2e`, `test:i18n`, `db:migrate`, `db:seed`다. 독립 서버/다운로드의 정확한 필터·환경·실패/재실행은 [Phase 8 체크리스트](phase8-test-checklist.md)에 기록한다. 원래 전체 Phase의 공급자 검증과 독립 검증을 구분한다.

실제 생성 fixture와 검증 결과 각 상태, 가이드 v1/v2·동시 요청·파일 누락·큰 ZIP. 실제 검증 품질은 합의 데이터/승인 환경에서 평가.

아래는 **실행 전 검증 설계**다. 구현이 끝나면 `phase8-test-checklist.md`에 환경·명령/절차·실제 결과·종료 코드·suite/test 성공/실패/skip 수·실패 원인·수정·재검증을 기록한다. 해당 Phase에 적용하지 않는 테스트 범주는 삭제하지 말고 `NOT_APPLICABLE` 사유와 이후 검증 Phase를 기록한다.

| ID | 필수 여부 | 분류 | 명령 또는 실행 절차 | 기대 결과 | 현재 상태 |
| --- | --- | --- | --- | --- | --- |
| P8-T01 | 필수 | 단위/공급자 | 규칙 판정·근거·버전·unknown·실제 평가 데이터 실행 | 임의 점수 제거·설명/근거 보존·합의 품질 충족 | PENDING |
| P8-T02 | 필수 | 통합/권한 | 반려/미검증/타인/구버전 직접 확정·동시 확정/취소 | 우회 0건·멱등성/충돌 정상·서버 판정 강제 | PENDING |
| P8-T03 | 필수 | E2E | 생성→채택→검증→최종→라이브러리·취소·가이드 변경 | 화면/DB 일관·원본 보존·버전 정책과 집계 정상 | PENDING |
| P8-T04 | 필수 | 파일/장애 | 단일/ZIP 다운로드·타인 파일/만료·worker 중단·재시도 | 유효한 파일/ZIP·소유권 강제·만료 정리·참조 파일 보존 | PENDING |
| P8-T05 | 필수 | 회귀 | 실제 생성부터 ZIP까지 새로고침/ko-en 전환 포함 실행 | 전 과정 실데이터 사용·언어 전환이 점수/원문/job 의미를 바꾸지 않음 | PENDING |

기본 코드 검사는 코드가 변경되는 Phase마다 필수다. 표의 필수 검증 중 하나라도 `FAIL/BLOCKED/PENDING`이면 완료할 수 없다. test adapter/sandbox 통과와 실제 공급자 품질 검증을 구분한다.

## 11. 완료 조건

- [ ] 반려/미검증/권한 없는 에셋의 최종 확정 우회가 불가능하다.

- [ ] 다음 Phase를 막는 미해결 항목이 없다.

## 12. 위험과 대응

검증 재실행으로 최신 요약이 바뀌어도 과거 근거는 jobs와 가이드 버전으로 남긴다. 다운로드 전 파일 경로·소유권을 재검사하며 큰 ZIP은 요청 프로세스에서 생성하지 않는다.

## 13. rollback/복구

검증/최종 쓰기·내보내기를 제한하고 호환 이전 handler로 복원한다. 잘못된 확정은 감사 가능한 보정으로 취소하되 원본·검증·가이드 이력은 삭제하지 않는다.

사용자 변경을 포함한 작업 트리를 통째로 초기화하지 않는다. 적용한 migration과 코드 버전의 호환성을 확인하며, 데이터가 존재하는 환경의 파괴적 되돌리기는 백업/복구 검증 없이 실행하지 않는다.

## 14. 결과 증거와 다음 Phase 인수인계

결과 증거: 상태 전이/동시성 결과·실제 평가 결과·전체 E2E·다운로드 checksum/ZIP 목록·버전 증거.

다음 단계: [Phase 9](phase9-plan.md)에 에셋/파일 참조·완성 job/adapter 패턴·파트너 공개 조회/번역 계약을 전달한다.

구현·검증 후 생성할 파일은 `phase8-test-checklist.md`, `phase8-result.md`, `phase8-result.html`이다. 현재 미생성 파일은 완료 증거로 링크하지 않는다. HTML은 외부 CDN/런타임 JavaScript 없이 단일 파일·반응형·인쇄 CSS로 작성한다. 로그·화면 증거에서 secret, 세션 쿠키, 개인정보, 비공개 원문을 제거한다. MD를 원본으로 삼고 두 보고서에 같은 완료 판정과 수치를 기록한다.

## 16. 2026-09-23 승인된 독립 구현 범위

사용자가 “실제 공급자는 보류하고 Phase 8 서버·다운로드부터 구현”을 선택했다. Phase 7 PAUSED는 유지하며 진행 규칙의 순차 게이트 예외를 이번 서버 구현에 한정한다. 기존 위의 미설치/미생성 설명은 초안 시점 기록이다. 현재 Next 16.3.3 로컬 route 가이드, Phase 7 MD/HTML·체크리스트, Phase 4~6 서버·큐·파일 계약을 확인했다. 기존 미커밋 변경은 보존한다.

- 담당: Codex 단독. 구현→격리 DB 통합·단위·언어팩·typecheck/lint/build→MD/HTML 보고.
- 공급자 미등록 시 검증 요청은 SERVICE_UNAVAILABLE이며 가짜 통과를 만들지 않는다. 주입 가능한 adapter 계약은 테스트 double로만 검증한다. 실제 평가·생성 전체 E2E는 보류이며 전체 Phase COMPLETED로 표시하지 않는다.
- 검증 요청은 채택된 같은 세션 에셋 최대 10개, 게시 가이드·규칙·에셋 version snapshot을 저장한다. pass/warn/reject/unknown과 근거·엔진을 보존하며 하나라도 pass가 아니면 최종화 금지. 기존 fail/review 기록과 호환한다. 부분/누락/중복 규칙 응답은 거절한다.
- 새 최종화는 최신 active 게시 가이드·succeeded job·일치하는 서버 근거가 필수. 과거 최종본은 당시 근거 보존, 재검증은 최종 취소 후 가능. version 충돌과 멱등 no-op을 구분한다. 취소는 원본 보존·에셋 지정 커버 해제.
- ZIP: 같은 프로젝트의 최종본 1~50개, 원본당 10MiB·합계 100MiB, worker에서 무압축 ZIP 생성. 입력 version snapshot·checksum·파일 유형/실제 크기·소유권을 생성/완료/다운로드에서 검사. 결과 24시간, 발급 ticket 최대 5분. 만료 결과는 접근 차단하며 기존 정리 ledger에 보존한다. 물리 삭제 정책은 변경하지 않는다.
- 새 의존성/테이블 없이 기존 JSONB 계약 확장, 최종화/검증/내보내기 API 및 다운로드 UI 연결. 파일·DB migration 필요성은 실제 변경 후 재평가.
- 검증 계획: 미검증/반려/unknown/구버전/타인 확정 거절, 동시 확정/취소, snapshot 충돌·늦은 결과, 유효 ZIP/checksum/만료/취소/소유권/누락/크기 한계, 기존 Phase 4~6 회귀.
- 재개 조건: 실제 Phase 7 게시·생성 연동 및 검증 공급자 선정/품질 평가 후 원래 P8-T01/T03/T05 전체 흐름 완료 판정.
