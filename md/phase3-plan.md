## 4. 현재 상태 조사

account-store는 로컬 계정이며 소셜 링크·프로필 URL로 인증 없이 진입 가능하다. 앱 layout에 서버 가드가 없다.

착수 기준은 기존 미커밋/미추적 변경이 포함된 현재 작업 트리다. Next 16.3.3, Better Auth 1.7.5, Drizzle, PostgreSQL 및 unit/integration/i18n/E2E 명령이 이미 설치되어 있다. 로컬 Next authentication/Route Handlers/cookies 가이드를 확인했다. 이전 Phase 사용자 파일을 보존하며 아래 착수/결정 기록에 조사 차이를 남겼다.

## 5. 구현 범위

이메일 선입력 후 신규/기존 분기, 신규 비밀번호 설정·회원가입 화면, 기존 회원 비밀번호 로그인, 가입 후 이메일 확인 링크, 비밀번호 찾기·재설정·현재 비밀번호 확인 후 변경, 서버 세션·로그아웃·프로필·정지/세션 폐기를 구현한다. 준비된 소셜 연결, API/페이지/파일 공통 권한 가드·최초 관리자 명령, 회원 언어 선호/계정 전환과 탈퇴 접근 차단·후속 파일 정리 계약을 포함한다.

이 단계에서 추가·변경하는 사용자/관리자 문구는 ko/en 파일 언어팩에 함께 반영한다. 업무 데이터 번역은 `localized_contents`만 사용하고, 고정 UI·랜딩·메일 문구는 DB로 옮기지 않는다.

## 6. 제외 범위

업무 CRUD·완성 어드민·조직 공유. 파일 정리는 Phase 4~5와 연결하며 이 단계에서 전체 탈퇴 정리 완료로 기록하지 않는다.

결제·구독, 조직 협업, 범용 CMS, 자동 침해 신고는 전체 초기 범위에서 제외한다. 새로운 비용·제품 정책·공개 계약이 필요하면 구현 전에 전체 플랜과 이 문서의 변경 이력을 갱신한다.

## 7. 결정·가정·질문

Phase 0에서 이메일·비밀번호 방식으로 확정했다. 이메일 입력 → 미가입: 비밀번호 설정·회원가입 → 이메일 확인 → 프로필 → 앱; 기존 회원: 비밀번호 로그인 → 프로필/앱 흐름이다. 이메일 조회는 nextStep만 반환하며 그 응답 자체는 인증이 아니다. 조회 후 동시 가입은 최종 UNIQUE 검사로 처리한다. OTP 로그인은 도입하지 않는다. 비밀번호 정책·메일 토큰 만료/시도 제한·세션·메일·관리자 추가 인증은 전체 플랜 D-01~02를 착수 전에 확정한다. D-03 보존 정책도 탈퇴 구현 전 확정한다. 이메일 일치로 소셜 자동 병합 금지, job_role/app_role 분리. 초기 cookie→회원→브라우저→ko와 계정 전환 시 회원 선호 동기화를 구분한다.

권장안과 확정 사항을 구분한다. 이 문서 작성에는 추가 승인이 필요하지 않으며, 미결정 항목은 해당 구현의 시작 게이트에서 해결한다. 실제 과금·메일 발송·외부 데이터 변경 검증은 진행 규칙 8.6에 따라 승인된 대상과 환경에서만 수행한다.

## 10. 테스트 계획

기본 검사: `pnpm lint`, `pnpm typecheck`, `pnpm exec tsc --noEmit`, `pnpm build`. Phase 1에서 인수한 명령은 `pnpm test:unit`, `pnpm test:integration`, `pnpm test:e2e`, `pnpm test:i18n`, `pnpm db:migrate`, `pnpm db:seed`다. corepack pnpm 10.34.5와 Docker test/web target을 사용하며 실제 명령과 종료 코드는 phase3-test-checklist.md에 기록한다. 테스트가 0개이거나 필수 suite가 skip이면 통과로 처리하지 않는다.

사용자 A/B·미가입/기존/이메일 미확인·일반/관리자·정지/탈퇴 fixture, 잘못된 비밀번호·동시 중복 가입·만료/재사용 확인/재설정 토큰·복구 후 이전 세션 fixture와 메일 sandbox를 사용한다. 실제 발송은 승인 대상만.

아래는 **실행 전 검증 설계**다. 구현이 끝나면 `phase3-test-checklist.md`에 환경·명령/절차·실제 결과·종료 코드·suite/test 성공/실패/skip 수·실패 원인·수정·재검증을 기록한다. 해당 Phase에 적용하지 않는 테스트 범주는 삭제하지 말고 `NOT_APPLICABLE` 사유와 이후 검증 Phase를 기록한다.

## 12. 위험과 대응

메일/소셜 공급자 미준비를 test adapter 성공으로 감추지 않는다. layout 검사와 별도로 모든 API/서비스에 권한 가드를 적용한다.

## 13. rollback/복구

신규 로그인 제한 후 호환 이전 서버 인증 버전 복원. 임시 브라우저 인증으로 되돌리지 않고 잘못 발급된 세션 폐기.

사용자 변경을 포함한 작업 트리를 통째로 초기화하지 않는다. 적용한 migration과 코드 버전의 호환성을 확인하며, 데이터가 존재하는 환경의 파괴적 되돌리기는 백업/복구 검증 없이 실행하지 않는다.

## 14. 결과 증거와 다음 Phase 인수인계

결과 증거: 인증/권한 테스트 수·마스킹된 메일 결과·계정 전환/프로필·탈퇴 후 거절.

다음 단계: [Phase 4](phase4-plan.md)에 인증 주체·소유권 가드·관리자 fixture·탈퇴/보존 정책을 전달한다.

구현·검증 후 생성할 파일은 `phase3-test-checklist.md`, `phase3-result.md`, `phase3-result.html`이다. 현재 미생성 파일은 완료 증거로 링크하지 않는다. HTML은 외부 CDN/런타임 JavaScript 없이 단일 파일·반응형·인쇄 CSS로 작성한다. 로그·화면 증거에서 secret, 세션 쿠키, 개인정보, 비공개 원문을 제거한다. MD를 원본으로 삼고 두 보고서에 같은 완료 판정과 수치를 기록한다.

- 공통 SSR/cookie 언어는 lib/i18n/server.ts의 requestLanguage를 사용한다. 회원 선호 슬롯은 아직 undefined다. 검증된 세션의 users.preferences.locale 연결, 첫 로그인 현재 locale 저장 및 계정 전환 동기화를 Phase 3에서 구현한다.

## 사용자 결정 및 확정 실행 범위 (2026-09-23)

사용자: “비밀번호 8자부터 가능하게하고 나머지는 권장안대로 하자”. D-01~03 개발용 기준 확정. READY 계획 공유 후 IN_PROGRESS로 전환한다.

- 비밀번호 8~128자, 세션 7일, 확인 토큰 24시간, 재설정 토큰 1시간. Better Auth의 검증된 password hash/verify 구현을 사용한다. 기존 auth schema 위에 명시적 서비스/API를 구성하여 계정 행 잠금과 토큰 단회 소비·세션 폐기를 같은 transaction에서 처리한다. OAuth endpoint는 노출하지 않는다.
- DB 기반 제한: endpoint별 IP 100회/15분, 이메일별 lookup/login 10회/15분, 가입/메일 5회/15분, 토큰 소비/비밀번호 변경은 인증 주체 또는 토큰 digest별 10회/15분. 신뢰 프록시를 명시하지 않으면 임의 forwarded IP를 믿지 않고 공통 unknown bucket으로 제한한다.
- 메일은 명시적 sandbox adapter만 제공한다. ko/en 메일을 웹 공개 경로 밖의 권한 제한 디렉터리에 저장한다. 실메일은 미구현/미검증으로 보고하며 외부 공급자 준비 후 별도 검증한다. sandbox 사용을 명시하지 않은 환경에서는 가입/복구 발송을 거절한다.
- 소셜 로그인 및 공개 관리자 접근은 비활성화한다. 관리자 승격/정지는 명시적 CLI 및 감사 기록으로 제공한다. 실제 관리자 이메일/추가 인증은 운영 공개 전 게이트로 남긴다.
- 탈퇴는 withdrawal_pending으로 전환하고 세션/토큰을 폐기한다. 업무/파일/감사/백업의 영구 삭제·익명화는 실행하지 않는다. 후속 Phase는 상태와 소유권을 검사하고 작업/파일 정리 정책을 별도로 확정한다.
- Phase 3 완료 판정은 위 승인된 로컬 개발 범위와 필수 합성 검증을 대상으로 한다. 실제 발송·OAuth·공개 관리자·영구 삭제를 완료로 주장하지 않는다.
- 신규 DB migration은 공유 rate-limit bucket만 추가한다. 세션/메일 토큰은 무작위 원문 대신 digest를 저장하고 sandbox 외 API/로그에 토큰을 노출하지 않는다.
