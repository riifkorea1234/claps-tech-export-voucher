## 1. 결론 (초보자 기준)

**판정: 미흡 — 설명 없이 초보 운영자에게 맡기기 어렵다.**

서버 쪽 기반은 탄탄하다. 모든 관리 API는 `AdminAccess.run`으로 권한·세션·15분 재확인을 다시 검사하고, 변경마다 사유·감사 기록·version 충돌 검사가 있다. 비관리자는 `/admin`에서 404를 받는다.

하지만 화면은 "이미 시스템을 아는 개발자"를 전제로 한다. 초보자 관점의 주요 문제는 다음과 같다.

1. 재확인(15분) 만료 시 편집하던 폼이 사라지고, 원래 작업은 다시 실행되지 않는다. 그런데도 "처리했습니다"가 표시된다.
2. 이용 정지·세션 폐기·작업 취소·보관 같은 영향 큰 작업에 확인 단계가 없다. 관리자가 자기 세션을 폐기할 수도 있다.
3. 실제로는 아무 변화가 없는 작업(예: 완료된 작업 "취소 요청")에도 "처리했습니다"가 표시된다.
4. 로딩 표시가 없다. 목록·상세·대시보드는 로딩 중에 빈 화면과 "1 / 1"만 보여 준다.
5. 대시보드 수치에서 다음 행동으로 이어지는 링크가 없다. 목록 이름 칸에는 원시 코드(`generation`)나 UUID가 보인다.
6. 가이드 메뉴에 "Phase 7에서 제공됩니다"라는 내부 개발 용어가 노출되고, 계획된 기능 대부분이 없다.

### ADM-01 · P0 · 재확인 만료 시 편집 중인 입력이 사라지고, 원래 작업은 재실행되지 않는데 "처리했습니다"가 뜸

- **사용자 영향:** 파트너 설명이나 번역을 길게 작성하다 15분이 지나 저장하면 입력이 모두 사라진다. 비밀번호를 다시 입력하면 "처리했습니다"가 떠서 저장된 줄 착각한다. 실제로는 저장되지 않았다.
- **위치:** `components/admin/console.tsx:105-107`(`reauth ? <form> : <>…본문…</>` 삼항 분기), `:78-93`(`act`가 항상 `admin.saved` 표시), `:48-52`(`failed`)
- **재현/관찰 [코드]:** ① 파트너 상세에서 설명 수정 → ② DB에서 `admin_verified_until`이 지나거나 15분 대기 → ③ 저장 → API가 `ADMIN_REAUTH_REQUIRED` 반환 → `setReauth(true)` → 본문 전체(`ResourceEditor`·`TranslationEditor`)가 언마운트되어 로컬 state가 사라진다 → ④ 비밀번호 확인 → `act`가 "처리했습니다" 표시 → `reload`로 서버 값을 다시 불러오므로 편집 전 값이 보인다. (E2E `admin.spec.ts`의 만료 검사는 "비밀번호 입력란 노출"까지만 본다.)
- **수정안:**
  1. 재확인 폼을 본문 **대신** 렌더링하지 말고, 본문 위의 모달/`<dialog>` 또는 상단 패널로 띄운다. 본문은 계속 마운트된 상태로 둔다(`hidden`/`inert` 사용 가능).
  2. `failed`가 `ADMIN_REAUTH_REQUIRED`를 받으면 실패한 작업 함수를 `pendingRef`에 보관한다. 재확인에 성공하면 "비밀번호를 확인했습니다. 요청을 다시 실행합니다." 안내 후 보관한 작업을 1회 자동 재실행한다. 사용자가 원하면 취소할 수 있게 한다.
  3. 재확인 성공 메시지는 `admin.reauthDone`(신규 키)로 따로 두고 `admin.saved`와 분리한다.
- **수용 기준:** 편집 폼에 값을 입력한 상태에서 세션 재확인을 만료시키고 저장 → 재확인 → 입력값이 그대로 남아 있고 저장이 1회 실행되어 서버 값에 반영된다. "처리했습니다"는 실제 저장이 성공한 뒤에만 뜬다. 이 시나리오를 `tests/e2e/admin.spec.ts`에 추가한다.

### ADM-02 · P0 · 이용 정지·세션 폐기·작업 취소·보관·공개 전환에 확인 단계가 없고, 자기 세션 폐기도 가능함

- **사용자 영향:** 초보자는 버튼 이름만 보고 누르기 쉽다. "모든 세션 폐기"는 대상 회원을 즉시 로그아웃시키고, 비밀번호 재설정·이메일 확인 토큰도 지운다(`service.ts:140-141`). 관리자가 **자기 계정** 상세에서 누르면 자신이 바로 로그아웃된다(정지는 막혀 있지만 revoke는 막혀 있지 않다). 프로젝트 "보관"은 체크박스+저장이라, 다른 필드를 고치다 함께 반영될 수 있다.
- **위치:** `console.tsx:182`(회원 정지/해제/폐기), `:183`(작업 재시도/취소), `:184`(모니터링 보관/복구/탐지), `:179`(프로젝트 보관 체크박스, 파트너 공개 범위 select), `lib/server/admin/service.ts:134-141`(`suspend`만 자기 자신 차단)
- **재현/관찰 [코드]:** 버튼 `onClick`이 곧바로 `act(() => request(...))`를 실행한다. `confirm`/다이얼로그가 없고, 모든 버튼이 같은 기본 variant다. 회원 상세에서 `revoke`는 `id === u.id`여도 통과한다.
- **수정안:**
  1. 공통 `ConfirmAction` 컴포넌트(기존 UI 컴포넌트 재사용, `<dialog>` 또는 기존 dialog가 있으면 그것)를 만든다. 제목, 결과 설명(예: "이 회원은 즉시 로그아웃되고 다시 로그인할 수 없습니다"), 대상 이름, 입력한 사유 요약, [취소]/[실행] 버튼을 둔다. 실행 버튼은 `variant="destructive"`로 한다.
  2. 적용 대상: 회원 `suspend`·`revoke`, 작업 `cancel`, 모니터링 `archive`, 프로젝트 보관 **체크 상태 변경이 포함된 저장**, 파트너 `private→public`/`public→private` 변경이 포함된 저장.
  3. 서버: `user()`의 `revoke`도 `id === u.id`면 `STATE_CONFLICT`로 막는다(또는 화면에서 자기 계정일 때 버튼 숨김 + 서버 차단 둘 다). 자기 계정 상세에는 "본인 계정은 여기서 정지·세션 폐기할 수 없습니다"를 표시한다.
  4. 결과 설명 문구를 `admin.json`에 ko/en으로 추가한다(`confirm.suspend`, `confirm.revoke`, `confirm.cancelJob`, `confirm.archive`, `confirm.visibility` 등).
- **수용 기준:** 위 작업은 확인 다이얼로그에서 [실행]을 눌러야만 API가 호출된다. [취소]나 Esc를 누르면 호출되지 않는다. 자기 계정 revoke는 화면에서 불가하고, API 직접 호출도 409/STATE_CONFLICT다(통합 테스트 추가). 다이얼로그는 키보드만으로 조작할 수 있고, 열리면 포커스가 다이얼로그 안으로, 닫히면 원래 버튼으로 돌아간다.

### ADM-03 · P0 · 불가능하거나 효과 없는 작업에도 버튼이 활성이고 "처리했습니다"가 뜸

- **사용자 영향:** 이미 성공/실패한 작업에 "취소 요청"을 누르면 서버는 상태를 바꾸지 않는데도 감사 기록을 남기고 성공을 반환한다. 화면에는 "처리했습니다"가 뜬다. 초보자는 취소됐다고 믿는다. "재시도"도 이미 재시도된 작업이면 기존 자식 작업을 돌려줄 뿐인데 똑같이 "처리했습니다"가 뜨고, 새 작업으로 이동하는 링크도 없다. 재시도가 불가능한 상태면 원인 없는 "현재 상태에서 실행할 수 없습니다"가 뜬다.
- **위치:** `console.tsx:183`(재시도/취소 버튼이 상태와 무관하게 항상 렌더링됨), `:84`(항상 `admin.saved`), `lib/server/admin/service.ts:188-207`(`cancel`은 queued/running이 아닐 때 no-op 후 audit 및 성공 반환), `:72`(상세 응답에 `canRetry`/`canCancel`이 없음. `jobDto` 미사용), `lib/server/jobs/service.ts:76-83`(`retryLocked`: 기존 자식 반환 / `canRetry` 아니면 STATE_CONFLICT)
- **재현/관찰 [코드]:** `status='succeeded'` 작업 상세 → 사유 입력 → "취소 요청" → 200, 상태 변화 없음, 화면에 "처리했습니다".
- **수정안:**
  1. 서버 상세(`detail` 중 `jobs`)에 `jobDto`의 `canRetry`, 그리고 `canCancel`(queued/running 여부)을 포함한다. 가능하면 `retryJobId`(`retry_of_id=$id`인 자식)도 넣는다.
  2. `job()`의 `cancel`에서 대상이 queued/running이 아니면 `STATE_CONFLICT`를 던진다(감사 기록 없음).
  3. 화면: 불가능한 버튼은 숨기거나 비활성화하고, 옆에 이유를 표시한다(예: "이미 완료된 작업은 취소할 수 없습니다", "응답이 불확실한 작업은 중복 과금 위험 때문에 재시도할 수 없습니다"). 재시도에 성공하면 "새 작업을 만들었습니다 → [새 작업 열기]" 링크를 보여 준다.
  4. `act`에 성공 메시지 키를 인자로 받게 한다(`act(fn, "admin.done.cancelRequested")`). 결과 상태에 맞는 문장을 표시한다(예: 실행 중 작업 취소는 "취소를 요청했습니다. 외부 처리 완료 여부는 작업 상태에서 확인하세요.").
- **수용 기준:** succeeded/failed/canceled 작업에는 취소 버튼이 없거나 비활성이며 이유가 보인다. API로 강제 호출하면 409이고 감사 기록이 늘지 않는다(통합 테스트). 재시도에 성공하면 새 작업 링크가 보인다. 성공 메시지가 작업 종류별로 다르다.

### ADM-08 · P1 · 오류 메시지에 원인과 해결 방법이 없음

## 6. 잘 된 점 (유지할 것)

- 모든 관리 API가 서버에서 권한·활성 상태·세션·15분 재확인을 매번 검사한다(`access.ts:90-117`). 페이지 가드(`page.tsx:5-7`)에만 의존하지 않는다.
- 변경은 `reason` 필수, `version` 낙관적 잠금, 감사 기록이 한 transaction으로 묶여 있다.
- 비관리자에게 404를 주어 관리 화면 존재를 숨긴다. [실측] 비로그인 API는 401이다.
- 상세 조회 자체도 감사 대상이다(`service.ts:94`).
- ko/en 문구 파일 구조와 언어 전환 중 폼 유지가 E2E로 검증되어 있다.

## 7. coder 권장 작업 순서

1. **ADM-01 → ADM-02 → ADM-03** (P0). 공통 `act`/확인 다이얼로그/성공 문구 구조를 먼저 바꾸면 이후 항목이 쉬워진다.
2. **ADM-04, ADM-07, ADM-08** — 로딩·사유·오류 표시를 공통 컴포넌트(`Field`에 hint/error, 공통 알림, 로딩 상태)로 해결한다.
3. **ADM-06, ADM-11** — 메뉴별 열 정의와 `RecordView` 포맷터. 서버 목록 컬럼 추가(email, 가이드 프로젝트명)가 필요하다.
4. **ADM-05, ADM-10, ADM-09** — 대시보드 안내/링크, URL 필터, 진입 링크, 문구 정리.
5. P2(ADM-12~17)는 여유가 있을 때 처리한다.
