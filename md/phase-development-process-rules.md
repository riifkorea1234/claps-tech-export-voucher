# Phase 기반 개발 플랜 및 진행 규칙

## 1. 목적

이 문서는 프로젝트를 여러 Phase로 나누어 진행할 때 사용하는 공통 개발 운영 규칙이다. 특정 언어, 프레임워크, 제품에 의존하지 않으며 다른 프로젝트 저장소에 복사해 사용할 수 있다.

핵심 목표는 다음과 같다.

- 구현 전에 범위와 완료 기준을 고정한다.
- 이전 Phase의 결과와 이월 항목을 다음 Phase가 이어받는다.
- 실행하지 않은 테스트나 미완료 작업을 완료로 오인하지 않는다.
- 계획, 실제 구현, 테스트 결과와 인수인계 기록을 추적 가능하게 유지한다.
- 사용자 또는 의사결정권자가 중요한 변경을 구현 전에 확인할 수 있게 한다.

## 2. 기본 원칙

1. Phase 시작 요청을 받아도 바로 코드를 변경하지 않는다.
2. 각 Phase는 반드시 상세 개발 플랜을 먼저 작성한다.
3. 이전 Phase의 계획, 결과, 미완료 항목을 현재 Phase의 입력으로 사용한다.
4. 상세 플랜을 공유한 후 구현을 시작한다.
5. 구현 방향을 바꾸는 미결정 사항은 질문하고 결정한 뒤 진행한다.
6. 구현이 끝나면 Phase 전용 테스트 체크리스트를 만들고 실제 테스트를 수행한다.
7. 필수 테스트가 모두 통과한 뒤 Markdown과 HTML 결과 보고서를 작성한다.
8. 완료 조건과 보고 게이트를 모두 충족해야 다음 Phase를 시작한다.
9. 실패, 미실행, 차단 상태를 성공으로 기록하지 않는다.
10. 기존 사용자 변경과 현재 Phase 변경을 구분하고, 관련 없는 변경을 되돌리지 않는다.

## 3. 표준 파일 구조

프로젝트의 문서 디렉터리가 `md/`라고 가정한다. 다른 디렉터리를 사용하면 모든 경로를 동일한 규칙으로 변경한다.

```text
md/
  development-plan.md
  phase0-plan.md
  phase0-test-checklist.md
  phase0-result.md
  phase0-result.html
  phase1-plan.md
  phase1-test-checklist.md
  phase1-result.md
  phase1-result.html
  ...
```

Phase N의 필수 산출물:

```text
md/phase{N}-plan.md
md/phase{N}-test-checklist.md
md/phase{N}-result.md
md/phase{N}-result.html
```

파일명은 공백 없이 소문자와 숫자, 하이픈을 사용한다. 한 프로젝트 안에서는 번호 표기와 디렉터리 위치를 바꾸지 않는다.

## 4. 전체 실행 순서

모든 Phase는 다음 순서로 진행한다.

```text
이전 Phase 검토
→ 저장소와 요구사항 조사
→ 상세 개발 플랜 작성
→ 플랜 요약 공유 및 필요한 결정 확인
→ 구현
→ 테스트 체크리스트 작성
→ 테스트 실행
→ 실패 수정 및 재테스트
→ Markdown/HTML 결과 보고서 작성
→ 완료 판정
→ 다음 Phase 인수인계
```

순서를 생략하거나 결과 보고서를 테스트보다 먼저 확정하지 않는다.

## 5. Phase 시작 게이트

### 5.1 시작 전 확인 자료

Phase N을 시작하기 전에 다음 자료를 순서대로 확인한다.

1. 프로젝트 전체 개발 플랜과 아키텍처/계약 문서
2. 현재 저장소 구조, 관련 코드, 테스트, 데이터와 작업 트리 상태
3. `phase{N-1}-plan.md`
4. `phase{N-1}-test-checklist.md`
5. `phase{N-1}-result.md`, `phase{N-1}-result.html`
6. 이전 Phase의 미완료 항목, 위험, 결정과 인수인계
7. 현재 Phase와 다음 Phase 사이의 범위 및 의존성

Phase 0은 이전 Phase가 없으므로 요구사항, 기존 시스템, 저장소 상태와 이해관계자 결정을 입력으로 사용한다.

### 5.2 이전 Phase 완료 확인

Phase 1 이상은 바로 이전 Phase가 다음 조건을 만족하는지 확인한다.

- 결과 보고서 상태가 `COMPLETED`다.
- 필수 테스트가 모두 `PASS`다.
- 미완료 항목이 현재 Phase 시작을 막지 않는다.
- 필요한 migration, 데이터, API와 설정이 인수인계되어 있다.

이전 Phase 문서가 없거나 완료 상태가 아니면 현재 Phase 구현을 시작하지 않는다. 누락된 문서를 복원하거나 차단 항목을 해결한 뒤 다시 시작한다.

## 6. 상세 개발 플랜 규칙

### 6.1 작성 시점과 상태

구현 파일을 수정하기 전에 `phase{N}-plan.md`를 작성한다. 조사 과정의 읽기 전용 명령은 허용하지만, 코드·DB·설정 변경은 플랜 작성과 공유 이후에 시작한다.

권장 계획 상태:

| 상태 | 의미 |
| --- | --- |
| `DRAFT` | 조사 또는 범위 정리가 진행 중 |
| `BLOCKED` | 사용자 결정이나 외부 조건이 필요함 |
| `READY` | 필요한 결정과 선행 조건이 충족되어 구현 가능 |
| `IN_PROGRESS` | 상세 플랜에 따라 구현 중 |
| `EXECUTED` | 구현과 검증이 끝나 결과 보고 단계로 이동 |

### 6.2 상세 플랜 필수 내용

`phase{N}-plan.md`에는 다음 내용을 포함한다.

1. Phase 번호, 제목, 상태, 작성일, 예상 기간
2. 배경, 목표와 완료 후 사용자/운영 가치
3. 입력 문서와 이전 Phase 인수인계 요약
4. 현재 저장소 상태와 관련 기존 구현
5. 구현 범위와 명시적인 제외 범위
6. 확정 결정, 가정과 추가 결정이 필요한 항목
7. 작업 분해 구조와 실행 순서
8. 작업별 산출물, 의존성과 담당 영역
9. 예상 생성·변경·삭제 파일
10. DB migration, seed, API, 화면, 인프라 영향
11. 단위·통합·E2E·수동 검증 계획과 실행 명령
12. 완료 조건과 정량 기준
13. rollback/복구 방법
14. 위험, 대응과 범위 확장 가능성
15. 결과 보고서에 남길 증거
16. 다음 Phase 인수인계 예상 항목
17. 플랜 변경 이력

### 6.3 상세 플랜 작성 절차

1. 관련 문서와 파일을 읽는다.
2. 기존 변경과 현재 Phase가 소유할 변경을 구분한다.
3. 요구사항을 사용자 흐름과 시스템 동작으로 분해한다.
4. 선행 의존성과 위험이 높은 작업을 먼저 식별한다.
5. 작업을 독립적으로 검증 가능한 단위로 나눈다.
6. 각 작업의 산출물과 테스트를 연결한다.
7. 완료 조건이 모호하면 측정 가능한 조건으로 바꾼다.
8. 사용자 결정이 필요한 항목을 권장안과 함께 질문한다.
9. 결정이 끝나면 상태를 `READY`로 변경하고 플랜을 공유한다.

### 6.4 질문이 필요한 경우

다음 조건 중 하나에 해당하면 구현 전에 질문한다.

- 서로 다른 선택이 데이터 모델이나 API 계약을 바꾸는 경우
- 결제, 삭제, 공개 범위, 개인정보 보존 같은 제품 정책이 필요한 경우
- 외부 공급자, 비용, 계정 또는 권한 선택이 필요한 경우
- 파괴적 변경이나 복구하기 어려운 작업이 필요한 경우
- 기존 요구와 새로운 요청이 충돌하는 경우
- 합리적인 기본값을 선택하면 사용자 의도와 크게 달라질 가능성이 있는 경우

질문할 때는 선택지, 권장안, 영향과 trade-off를 함께 제시한다. 결정 전까지 관련 작업은 `BLOCKED`로 표시하되 독립적인 조사와 준비 작업은 계속할 수 있다.

## 7. 구현 진행 규칙

### 7.1 작업 단위

- 상세 플랜 순서대로 구현한다.
- 각 작업은 산출물과 검증 방법을 가져야 한다.
- 관련 없는 리팩터링이나 기능 확장을 끼워 넣지 않는다.
- 사용자 소유 변경을 보존하고 겹치는 파일은 diff를 확인한 뒤 수정한다.
- 데이터 손실 가능성이 있는 작업은 대상을 읽기 전용으로 확인하고 복구 방법을 마련한다.

### 7.2 진행 공유

장시간 작업에서는 다음 시점에 간결하게 진행 상황을 공유한다.

- 조사와 상세 플랜 작성 완료
- 중요한 결정 또는 위험 발견
- 주요 구현 단위 완료
- 테스트 시작
- 실패 원인과 수정 방향 확인
- Phase 완료 또는 차단

진행 공유는 최종 결과를 대신하지 않는다. 최종 보고서는 이전 메시지를 읽지 않아도 이해할 수 있어야 한다.

### 7.3 플랜 변경 통제

상세 플랜에 없는 작업이 필요하면 구현 전에 플랜 변경 이력을 갱신한다.

다음 변경은 영향 범위를 사용자에게 알리고 필요한 결정을 받은 뒤 진행한다.

- Phase 범위 추가 또는 제외 범위 철회
- DB schema나 공개 API 계약 변경
- 새로운 외부 서비스나 운영 비용 추가
- 보안·개인정보·권한 정책 변경
- 일정 또는 완료 조건의 의미 있는 변경
- 파괴적 migration이나 호환성 중단

결과 보고서에는 최초 플랜과 실제 구현의 차이, 변경 이유와 영향을 기록한다.

## 8. 테스트 체크리스트 규칙

### 8.1 작성 시점

구현이 끝나면 결과 보고서 작성 전에 `phase{N}-test-checklist.md`를 작성한다. 상세 플랜의 검증 계획을 실제 실행 가능한 항목으로 변환한다.

### 8.2 테스트 상태

| 상태 | 의미 |
| --- | --- |
| `PASS` | 기대 결과 충족 |
| `FAIL` | 실행했으나 기대 결과 미충족 |
| `BLOCKED` | 환경이나 외부 조건으로 실행 불가 |
| `NOT_APPLICABLE` | Phase 범위에 해당하지 않으며 근거가 있음 |
| `PENDING` | 아직 실행하지 않음 |

### 8.3 체크리스트 필수 내용

1. Phase 번호, 테스트 상태, 실행일과 환경
2. 선행 조건과 사용한 데이터/fixture
3. 테스트 ID와 분류
4. 필수 여부
5. 대상 기능
6. 실행 명령 또는 수동 절차
7. 기대 결과
8. 실제 결과와 상태
9. suite/test 성공·실패·skip 수
10. 실패 원인과 수정 내용
11. 재테스트 결과
12. 실행하지 않은 테스트의 사유와 위험
13. Phase 완료 가능 여부

### 8.4 테스트 범주 선택

Phase 성격에 맞춰 다음 항목을 선택한다.

- lint와 formatting
- typecheck
- build
- 단위 테스트
- 통합 테스트
- E2E 테스트
- migration과 rollback/forward-fix
- seed 최초 실행과 재실행 멱등성
- API/OpenAPI 계약
- 인증, 권한과 보안
- 성능과 부하
- 접근성과 키보드 탐색
- 브라우저와 반응형 화면
- 장애, timeout과 외부 adapter fallback
- 수동 사용자 흐름

적용하지 않는 범주는 삭제하지 않고 `NOT_APPLICABLE` 사유와 이후 검증 Phase를 기록한다.

### 8.5 실행과 재테스트

- 명령과 수동 절차는 실제 실행 후 기록한다.
- 명령, 종료 코드, suite/test 수와 핵심 결과를 보존한다.
- 로그 전체 대신 재현에 필요한 요약과 안전한 증거를 남긴다.
- 실패를 수정하면 최초 결과와 재테스트 결과를 모두 기록한다.
- 수정 범위에 영향을 받는 관련 테스트도 다시 실행한다.
- 필수 테스트가 `FAIL`, `BLOCKED`, `PENDING`이면 Phase를 완료하지 않는다.

### 8.6 테스트 증거 보안

다음 정보는 체크리스트와 로그 증거에서 제거하거나 마스킹한다.

- 비밀번호와 token
- 인증 코드와 세션 쿠키
- 개인 정보와 운영 사용자 데이터
- 외부 서비스 secret과 connection string
- 비공개 사용자 콘텐츠 전문
- 보안 취약점 악용에 필요한 민감 세부 정보

외부 서비스 테스트는 test double 또는 sandbox를 우선한다. 실제 과금, 메일 발송, 외부 데이터 변경은 명시적인 승인과 대상 확인 없이 실행하지 않는다.

## 9. Phase 완료 보고 규칙

### 9.1 결과 보고서

테스트가 끝나면 다음 두 파일을 작성한다.

```text
md/phase{N}-result.md
md/phase{N}-result.html
```

Markdown을 원본 기록으로 사용하고 HTML은 사람이 읽고 공유하기 쉬운 독립 보고서로 사용한다. 두 파일은 같은 사실, 수치와 판정을 담아야 한다.

### 9.2 결과 보고서 필수 내용

1. Phase 번호, 제목, 상태, 작업 기간과 완료일
2. 목표와 실제 완료 범위
3. 상세 플랜 대비 실제 구현 차이
4. 주요 결정과 구현 내용
5. 생성·변경·삭제 파일
6. migration, seed, API와 화면 변경
7. 테스트 체크리스트 링크
8. 실행한 테스트와 정량 결과
9. 수동 검증 증거
10. 완료 조건별 체크리스트
11. 미완료 항목과 알려진 문제
12. 위험과 다음 Phase 이월 작업
13. 다음 Phase 착수에 필요한 인수인계

### 9.3 HTML 보고서 규칙

HTML 보고서는 다음 조건을 만족한다.

- 외부 CDN이나 런타임 JavaScript에 의존하지 않는 단일 파일
- 반응형 레이아웃과 인쇄 가능한 CSS
- 상태·기간·핵심 수치 요약
- 완료 조건 표와 테스트 결과 표
- 미완료·위험·인수인계 영역
- Markdown 보고서와 동일한 상태, 수치, 실패와 이월 항목
- secret과 개인 정보 미포함

## 10. 완료 게이트

다음 조건을 모두 만족해야 Phase를 `COMPLETED`로 표시한다.

- 상세 개발 플랜이 존재하고 실제 구현과 차이가 기록되어 있다.
- 계획된 필수 기능과 문서가 완료되었다.
- `phase{N}-test-checklist.md`가 존재한다.
- 모든 필수 테스트가 `PASS`다.
- `NOT_APPLICABLE` 테스트마다 사유와 위험이 있다.
- `phase{N}-result.md`와 `phase{N}-result.html`이 존재한다.
- 두 결과 보고서의 상태, 수치, 테스트와 미완료 항목이 일치한다.
- 결과 보고서가 테스트 체크리스트를 링크한다.
- 문서 링크와 HTML 구조가 검증되었다.
- 실패하거나 실행하지 못한 테스트를 성공으로 기록하지 않았다.
- 다음 Phase를 막는 미해결 항목이 없다.

조건을 충족하지 못하면 상태를 `IN_PROGRESS` 또는 `BLOCKED`로 유지한다.

## 11. 중단과 재개 규칙

작업이 중단되거나 다음 세션에서 재개될 때는 다음 순서로 복구한다.

1. 현재 Phase 상세 플랜과 상태를 읽는다.
2. 작업 트리와 최근 변경을 확인한다.
3. 완료된 작업과 미완료 작업을 실제 파일/테스트로 검증한다.
4. 이전 진행 메시지가 아니라 저장소 문서를 기준으로 재개한다.
5. 플랜 변경이 필요하면 변경 이력을 먼저 갱신한다.
6. 이미 통과한 테스트도 이후 변경의 영향을 받으면 재실행한다.

완료된 Phase를 다시 요청받으면 결과를 덮어쓰지 않는다. 먼저 완료 보고서와 체크리스트를 감사하고, 누락이나 회귀가 있을 때만 보완한다. 재감사 결과는 기존 기록의 사실성을 해치지 않도록 변경 이력이나 별도 재검증 항목으로 남긴다.

## 12. 예외와 차단 처리

다음 상황에서는 무리하게 완료 처리하지 않는다.

- 사용자 결정이나 권한이 필요한 경우
- 필요한 외부 계정/서비스가 준비되지 않은 경우
- 테스트 환경 장애로 필수 검증이 불가능한 경우
- 기존 변경과 충돌해 안전하게 수정할 수 없는 경우
- 요구사항이 서로 충돌하거나 완료 기준이 정의되지 않은 경우
- 데이터 손실 가능성이 있는데 복구 경로가 없는 경우

차단 보고에는 다음 내용을 포함한다.

- 정확한 차단 원인
- 이미 확인하거나 시도한 내용
- 영향을 받는 작업과 완료 조건
- 사용자가 제공해야 할 결정, 권한 또는 정보
- 차단 해소 후 재개 위치

## 13. 권장 상세 플랜 템플릿

```markdown
# Phase N 상세 개발 플랜

## 1. 기본 정보
## 2. 배경과 목표
## 3. 입력 자료와 이전 Phase 인수인계
## 4. 현재 상태 조사
## 5. 구현 범위
## 6. 제외 범위
## 7. 결정·가정·질문
## 8. 작업 분해와 실행 순서
## 9. 예상 파일/API/DB/화면 영향
## 10. 테스트 계획
## 11. 완료 조건
## 12. 위험과 대응
## 13. rollback/복구
## 14. 결과 증거와 다음 Phase 인수인계
## 15. 변경 이력
```

## 14. 권장 테스트 체크리스트 템플릿

```markdown
# Phase N 테스트 진행 체크리스트

## 1. 기본 정보와 환경
## 2. 상태 정의
## 3. 자동 테스트 체크리스트
## 4. 수동 테스트 체크리스트
## 5. 적용하지 않는 테스트와 사유
## 6. 실패·수정·재테스트 기록
## 7. 실행 결과 요약
## 8. Phase 완료 판정
```

각 테스트 행은 최소한 `ID | 필수 여부 | 분류 | 대상 | 명령/절차 | 기대 결과 | 실제 결과 | 상태`를 포함한다.


## 16. 최종 운영 체크리스트

### Phase 시작 전

- [ ] 이전 Phase가 `COMPLETED`인지 확인했다.
- [ ] 이전 계획·테스트·결과·이월 항목을 읽었다.
- [ ] 현재 저장소와 작업 트리 상태를 조사했다.
- [ ] `phase{N}-plan.md`를 작성했다.
- [ ] 범위, 제외 범위와 완료 조건을 명시했다.
- [ ] 필요한 질문과 결정을 해결했다.
- [ ] 상세 플랜을 공유하고 상태를 `READY`로 만들었다.

### 구현 중

- [ ] 상세 플랜의 작업 단위와 순서를 따랐다.
- [ ] 관련 없는 사용자 변경을 보존했다.
- [ ] 중요한 범위 변경 전에 플랜과 변경 이력을 갱신했다.
- [ ] 위험, 실패와 결정 내용을 숨기지 않고 기록했다.

### 구현 후

- [ ] `phase{N}-test-checklist.md`를 작성했다.
- [ ] 계획한 테스트를 실제 실행했다.
- [ ] 실패 수정과 재테스트 결과를 기록했다.
- [ ] 필수 테스트가 모두 `PASS`다.
- [ ] 적용 제외 테스트에 사유와 위험이 있다.
- [ ] Markdown/HTML 결과 보고서를 작성했다.
- [ ] 두 보고서와 테스트 체크리스트의 수치가 일치한다.
- [ ] 미완료·위험·인수인계를 기록했다.
- [ ] 모든 완료 게이트를 확인한 뒤 `COMPLETED`로 판정했다.
