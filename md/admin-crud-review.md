## 1. 결론

- 현재 어드민은 **메뉴 7개, 화면 상태 14개**다(대시보드 1(탭 3), 목록 6, 상세 6, 신규 1). 연관된 관리가 흩어져 있다. 가이드는 프로젝트와 분리된 별도 메뉴이고, 언어 관리·감사 기록은 "대시보드" 탭 안에 숨어 있으며, 번역 편집은 파트너 상세 폼 아래에 이어 붙어 있다.
- 상세 화면은 "보기"와 "수정"이 구분되지 않는다(항상 편집 폼). **삭제 버튼은 어느 도메인에도 없다.** 보관은 프로젝트 체크박스, 모니터링 버튼으로 제각각이고, 파트너와 파트너 이미지는 삭제·보관 수단이 전혀 없다.
- 권장 구조는 **메뉴 5개, 화면 템플릿 3종(대시보드/공통 목록/공통 상세), 화면 상태 10개**다. 가이드는 프로젝트 상세 탭으로 흡수한다. 작업·모니터링·감사 기록·언어는 "운영" 메뉴의 탭으로 묶는다. 상세는 한 화면에서 [수정]으로 편집 모드로 전환하고, 하단 "위험 구역"에 삭제(=보관/비활성) 버튼을 둔다.
- 물리 삭제는 제안하지 않는다. DB FK가 모두 `NO ACTION`이고 계획이 "보존 정책 확정 전 cascade 영구 삭제 금지"를 명시하기 때문이다(`md/development-plan.md:139,207,237,240,340`). 도메인별로 "삭제" 버튼이 실제로 무엇을 하는지 UI에 설명한다(4장).

CRUD 누락은 **9건**이다: 파트너 삭제, 파트너 이미지 삭제, 번역 게시 중단, 가이드 C/U/D, 프로젝트 삭제 버튼, 목록 보관 필터, 회원 탈퇴 대기 처리 안내, 감사 기록 필터, 모니터링 이름 수정. 의도된 예외는 **8건**이다: 감사 기록·작업·언어·회원·에셋/세션 삭제 금지, 회원/프로젝트/모니터링 관리자 생성 불가. 상세는 3장 매트릭스를 본다.

## 4. 삭제 버튼의 실제 의미 (UI 문구 기준)

모든 상세 화면 하단의 "위험 구역"에 삭제 계열 버튼을 **한 곳에** 둔다. 버튼 이름은 실제 동작 그대로 쓴다("삭제"라는 단어는 되돌릴 수 없는 동작에만 쓴다). 확인 다이얼로그에는 아래 "영향 설명"을 그대로 쓴다(ADM-02의 `ConfirmAction` 재사용).

### CRUD-01 · P0 · 파트너와 파트너 이미지를 삭제·보관할 수 없음

- **근거 [코드]:**
  - `partners` 테이블에 `archived_at`이 없다(`db/migrations/0000_foundation.sql:201-215`).
  - 관리 API는 생성·수정만 있다(`lib/server/admin/http.ts:53-54`).
  - 이미지는 추가만 가능하다(`lib/server/admin/images.ts:26,52-54`, 최대 20장).
  - `projects.partner_id → partners` FK는 `NO ACTION`이다(`0000_foundation.sql:281`). 공개 카탈로그·추천은 `visibility='public'`만 본다(`lib/server/partners/service.ts:35,39`, `lib/server/matching/service.ts:59,78`).
- **영향:** 잘못 등록한 파트너나 계약이 끝난 파트너를 치울 방법이 "비공개 전환"뿐이다. 그러면 관리자 목록에 초안과 종료 파트너가 섞인다. 잘못 올린 이미지는 공개 카탈로그에 계속 남고, 20장이 차면 더 올릴 수 없다.
- **구체안:**
  1. additive migration: `partners.archived_at timestamptz NULL`(drizzle `db/schema.ts` + `pnpm db:generate`). 기존 행은 NULL로 영향이 없다.
  2. `AdminService.partner`에 `archive`/`restore` 액션을 추가한다(또는 `POST partners/:id` `{action, version, reason}`로 `monitoring`과 같은 형태). archive는 `archived_at=now(), visibility='private', version+1` + 감사 `partner.archive`로 처리한다. 보관된 파트너는 PATCH로 `public` 전환을 거절한다(STATE_CONFLICT).
  3. 공개 조회(`partners/service.ts`, `matching/service.ts`)에 `AND archived_at IS NULL`을 추가한다(방어적 이중 조건).
  4. 이미지 삭제: `DELETE /api/admin/partners/:id/images/:index` 또는 `POST .../images/:index {action:"remove", version, reason}`. `profile.images`에서 제거하고, 파일은 기존 `storage_tickets` cleanup 흐름(`lib/server/storage/service.ts:27`의 cleanup 티켓 생성, `images.ts:28`과 같은 형태)으로 정리 예약하며(`state='cleanup_pending'`, 대시보드 "정리 대기"와 연결), 감사 `partner.image.remove`를 남긴다. `source_revision` 변화 여부는 기존 규칙(이미지는 번역 대상이 아님)에 맞춘다.
  5. UI: 파트너 상세 "이미지" 탭에서 각 썸네일에 [삭제](확인 다이얼로그, 4장 문구)를 두고, 위험 구역에 [보관]/[복구]를 둔다.
- **변경 범위:** `db/schema.ts`, 새 migration, `lib/contracts/admin.ts`, `lib/server/admin/{service,http,images}.ts`, `lib/server/partners/service.ts`, `lib/server/matching/service.ts`, `components/admin/*`, `messages/{ko,en}/admin.json`, `tests/integration/admin.test.ts`, `tests/e2e/admin.spec.ts`.
- **수용 기준:** 공개 파트너를 보관하면 `/api/partners`와 추천 후보에서 즉시 빠지고, 연결된 프로젝트의 `partner_id`는 유지된다. 복구하면 비공개 상태로 돌아온다. 보관 상태에서 공개 전환은 409다. 이미지를 삭제하면 카탈로그 이미지 수가 줄고 cleanup 티켓이 생긴다. 모든 동작이 감사 기록에 남고, 확인 다이얼로그 없이는 실행되지 않는다. version 충돌 시 409를 반환한다.

- **수용 기준:** 상세에 처음 들어오면 읽기 화면이다. [수정] → 폼 → [취소]하면 원래 값이 보이고 API 호출이 없다. [저장]에 성공하면 읽기 화면에 새 값이 보인다. 변경 후 다른 메뉴를 클릭하면 확인을 묻는다. 변경이 없으면 [저장]이 비활성이다.
