## 2. 배경과 목표

구현 방향을 바꾸는 정책과 기술 선택을 먼저 고정하고, 공급자 준비 책임과 완료 기준을 명확히 한다.

## 3. 입력 자료와 이전 Phase 인수인계

- [전체 개발 플랜](development-plan.md): 제품 범위·DB/API 계약·최종 완료 기준의 기준 문서.
- [Phase 진행 규칙](phase-development-process-rules.md): 시작·테스트·보고·완료 게이트.
- [기존 연동 가이드](../HANDOFF.md), [저장소 설명](../README.md), [AGENTS.md](../AGENTS.md).
- 이전 Phase 없음. 사용자 요구, 기존 UI/store/mock, 현재 작업 트리와 전체 플랜을 입력으로 사용한다.
- 필요한 인수인계: 전체 플랜 9절 결정표, 11개 기본 테이블 초안, 기존 UI 요구사항과 외부 엔진·배포 환경 준비 현황.

후속 Phase를 미리 계획하는 것은 허용하되 구현은 번호 순서대로 진행한다. 이전 Phase의 실패·차단·이월 항목이 이 단계의 완료 기준에 영향을 주면 먼저 해결하거나 범위/계약 변경을 기록한다.

## 4. 현재 상태 조사

착수 당시 UI만 존재하며 DB·서버 인증·worker는 없었다. 인증 방식·ORM은 이번 Phase에서 확정하고 공급자는 담당/기한을 정해 이월했다. 기존 HANDOFF의 테스트 수치는 재실행 증거가 아니다.

공통 조사 기준은 `feature/backend`의 현재 작업 트리다. 이번 문서 분할 시 `md/`는 기존 미추적 사용자 파일이었으며 원본 규칙을 보존한다. `package.json`에는 `dev/build/start/lint`만 있고 DB·인증·테스트 의존성은 없다. `node_modules/next/dist/docs/`는 현재 확인되지 않았다. 구현 착수 시 설치된 Next.js 버전의 로컬 가이드를 확보·확인한 뒤 코드를 작성한다. 이 문서는 미래 Phase의 코드가 이미 존재한다고 가정하지 않는다. 착수 시 실제 파일, 의존성, 작업 트리 및 이전 결과와 차이를 다시 기록한다.

## 5. 구현 범위

인증·소유권·보존·배포 정책, ORM/인증/테스트 도구와 버전, 테이블·DTO·상태 전이·권한 표를 확정한다. 전체 플랜 결정표에 선택·근거·담당·확정일·영향 Phase를 기록한다.

이 단계에서 추가·변경하는 사용자/관리자 문구는 ko/en 파일 언어팩에 함께 반영한다. 업무 데이터 번역은 `localized_contents`만 사용하고, 고정 UI·랜딩·메일 문구는 DB로 옮기지 않는다.

## 6. 제외 범위

코드 구현·의존성 설치·DB 생성·외부 호출. 기반 계약에 영향 없는 공급자 선택은 담당과 기한을 정해 해당 기능 Phase로 이월 가능.

결제·구독, 조직 협업, 범용 CMS, 자동 침해 신고는 전체 초기 범위에서 제외한다. 새로운 비용·제품 정책·공개 계약이 필요하면 구현 전에 전체 플랜과 이 문서의 변경 이력을 갱신한다.

## 7. 결정·가정·질문

2026-09-22 착수 조사 후 사용자에게 기반 선택을 확인했다. 권장안 승인 후 사용자가 인증을 **이메일 선입력·미가입 시 비밀번호 설정 및 회원가입 / 기존 회원 비밀번호 로그인**으로 정정했다. 개인 소유/PostgreSQL/Docker 단일 호스트는 유지한다. 기술 도구 선정과 후속 보존·공급자·비용 결정 이월은 승인 범위다. 기반 결정 확인 후 READY로 판단하고 플랜을 공유했으며 계약 반영 및 문서 검증을 수행했다. 상세 결정·이월 표는 전체 플랜 9.1~9.3절, 계약은 5.5·6.6절, 추적은 10.3절에 기록한다.

Phase 0의 외부 호출 제외는 메일·AI 등 실행/변경 호출에 적용한다. 도구 호환성 판단을 위한 공식 문서와 공개 패키지 레지스트리 읽기 전용 조회는 이번 조사에 포함한다. 설치·코드 변경·DB 생성은 하지 않는다. 보고서는 결정 대기 시 `BLOCKED` 조사 결과로만 작성하며 완료 보고서로 취급하지 않는다.

확정 범위는 어드민 7개 메뉴, ko/en, UI 파일 언어팩과 업무 번역 DB 분리다. 이메일·비밀번호, 개인 소유, PostgreSQL·단일 호스트 및 ORM·인증·검증 도구 버전을 확정했다(전체 플랜 9.1~9.2절). 삭제·탈퇴·감사 보존 기간, 관리자 추가 인증, 백업 위치/주기/RPO/RTO, 요청·비용 상한, 공급자 품질/지연 기준은 담당과 적용 Phase를 지정하고 미정 수치를 임의 확정하지 않는다.

권장안과 확정 사항을 구분한다. 이 문서 작성에는 추가 승인이 필요하지 않으며, 미결정 항목은 해당 구현의 시작 게이트에서 해결한다. 실제 과금·메일 발송·외부 데이터 변경 검증은 진행 규칙 8.6에 따라 승인된 대상과 환경에서만 수행한다.

## 10. 테스트 계획

읽기 전용 조사: `git status --short`, `git diff --stat`, `git log -1 --oneline`, `rg --files`, `cat package.json`. Markdown 링크와 필수 섹션 검사는 문서 검증 스크립트로 수행하고 실제 사용한 명령을 체크리스트에 남긴다. 구현이 없는 이 단계의 lint/typecheck/build, DB 실행, E2E는 `NOT_APPLICABLE`로 기록하고 Phase 1 이후에 실행한다.

문서/정적 조사만 수행한다. 런타임·DB·E2E 검증은 Phase 1 이후에 수행한다.

아래는 **실행 전 검증 설계**다. 구현이 끝나면 `phase0-test-checklist.md`에 환경·명령/절차·실제 결과·종료 코드·suite/test 성공/실패/skip 수·실패 원인·수정·재검증을 기록한다. 해당 Phase에 적용하지 않는 테스트 범주는 삭제하지 말고 `NOT_APPLICABLE` 사유와 이후 검증 Phase를 기록한다.

| ID | 필수 여부 | 분류 | 명령 또는 실행 절차 | 기대 결과 | 현재 상태 |
| --- | --- | --- | --- | --- | --- |
| P0-T01 | 필수 | 정적 | git 상태·파일 목록과 문서 현황 대조 | 기존 변경 구분, 근거 없는 완료 주장 0건 | PASS |
| P0-T02 | 필수 | 결정 감사 | 기반 구현 필수 결정마다 담당/선택/근거 확인 | Phase 1 차단 결정 0건; 후속 결정 담당/기한 기록 | PASS |
| P0-T03 | 필수 | 계약 리뷰 | A/B 사용자·일반/관리자·정상/충돌/삭제 사례로 계약 대조 | 소유권·상태·삭제·번역 책임 모순 0건 | PASS |
| P0-T04 | 필수 | 문서 추적 | 모든 요구 ID와 T-01~24의 Phase 매핑·링크 확인 | 누락/의존성 순환/깨진 링크 0건 | PASS |

기본 코드 검사는 코드가 변경되는 Phase마다 필수다. 표의 필수 검증 중 하나라도 `FAIL/BLOCKED/PENDING`이면 완료할 수 없다. test adapter/sandbox 통과와 실제 공급자 품질 검증을 구분한다.

## 12. 위험과 대응

외부 엔진 유무·도구 호환성이 일정에 영향을 준다. 제품 결정을 기술 담당이 임의 확정하지 않고 범위와 일정 영향을 기록한다.

## 13. rollback/복구

이번 문서 변경만 diff 단위로 복원하고 결정 변경 이유를 기록한다. 실행 데이터 변경 없음.

사용자 변경을 포함한 작업 트리를 통째로 초기화하지 않는다. 적용한 migration과 코드 버전의 호환성을 확인하며, 데이터가 존재하는 환경의 파괴적 되돌리기는 백업/복구 검증 없이 실행하지 않는다.
